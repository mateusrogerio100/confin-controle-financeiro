1Visão geral: o mapa do sistema

O ConFin é um sistema web dividido em três partes que conversam pela internet:

Figura 1 — As três camadas do ConFin e como elas se comunicam.
  • Front-end é tudo o que o usuário vê e toca: as telas, os botões, os gráficos. Ele roda no navegador do usuário (no celular ou no computador).
  • Back-end é o "cérebro" que fica num servidor na internet. Ele recebe os pedidos do front-end, aplica as regras (por exemplo, "o valor deve ser maior que zero"), conversa com o banco e responde.
  • Banco de dados é onde as informações ficam guardadas de forma permanente: usuários, famílias e despesas.
Analogia: um restaurante O front-end é o salão e o cardápio: é com ele que o cliente interage. O back-end é a cozinha: recebe o pedido, segue as receitas (regras de negócio) e prepara a resposta. O banco de dados é a despensa, onde os ingredientes ficam guardados. O garçom que leva os pedidos é a API. O cliente nunca entra na despensa: tudo passa pela cozinha.

2A linguagem: JavaScript

Conceito JavaScript (JS) nasceu em 1995 para dar interatividade às páginas web e hoje é a única linguagem que os navegadores executam nativamente. Sua especificação oficial chama-se ECMAScript (por isso você vê nomes como "ES2015" ou "ES6"). É uma linguagem interpretada (na verdade, compilada "na hora", por JIT), de tipagem dinâmica (uma variável pode guardar qualquer tipo) e multiparadigma (aceita estilo funcional e orientado a objetos).

Um JavaScript, dois "lugares" para rodar

Uma linguagem precisa de um ambiente de execução (runtime) que leia e execute o código. O JavaScript tem dois ambientes principais, e o ConFin usa os dois:

AmbienteOnde rodaO que consegue fazerNo ConFin
Navegador
(Chrome, Safari...)		No aparelho do usuárioManipular a tela (DOM), clicar, mostrar gráficos, guardar dados no localStoragePasta web/
Node.jsNo servidorLer arquivos, abrir portas de rede, conectar a bancos de dados. Não tem tela.Pasta api/

Por que escolhemos uma única linguagem? Com JavaScript nos dois lados, a equipe estuda uma linguagem só, reaproveita conhecimento (o mesmo async/await, o mesmo JSON) e troca de "lado" sem mudar de mentalidade. Essa combinação é tão comum que tem nome: JavaScript full-stack.

Recursos da linguagem que aparecem muito no nosso código

Módulos (import / export)

Cada arquivo é um módulo que exporta funções e importa as de outros arquivos. Isso organiza o código em partes pequenas e com responsabilidade clara. Usamos o padrão moderno ESM, ativado por "type": "module" no package.json.

api/src/routes/despesas.jsimport { query } from '../db.js';            // pega a função query de outro arquivo
import { notificarFamilia } from '../realtime.js';
...
export default router;                       // entrega o roteador para o server.js

Funções assíncronas (async / await)

Falar com o banco ou com a internet leva tempo (milissegundos que, para um computador, são uma eternidade). Em vez de travar esperando, o JavaScript usa Promises: "prometo te entregar o resultado quando ficar pronto". O await escreve isso de um jeito que parece sequencial:

api/src/routes/auth.js (login)const { rows } = await query('SELECT * FROM usuario WHERE email = $1', [email]);
if (!usuario || !(await bcrypt.compare(senha, usuario.senha_hash))) { ... }
Conceito: event loop O Node.js executa seu código em uma única thread, mas não fica parado esperando o banco. Enquanto uma consulta está "em voo", ele atende outros usuários. Quando a resposta chega, o event loop retoma a função de onde o await parou. Por isso um servidor Node simples aguenta muitas conexões simultâneas, desde que o código não faça contas pesadas que bloqueiem a thread.

Desestruturação, spread e template strings

const { familia_id, id: usuario_id } = req.usuario;   // pega campos de um objeto
const despesa = { ...rows[0], usuario_nome: req.usuario.nome }; // copia e acrescenta
socket.join(`familia:${familia_id}`);                // texto com variável dentro

JSON: o idioma da conversa

JSON (JavaScript Object Notation) é o formato de texto que o front-end e o back-end usam para trocar dados. Por exemplo, quando o Carlos salva uma despesa, o celular envia:

{ "valor": 420.90, "categoria": "MERCADO", "meio_pagamento": "PIX", "data": "2026-11-09", "descricao": "Compra do mês" }
Atenção Por ter tipagem dinâmica, o JavaScript não avisa quando você passa um texto onde esperava um número. Por isso o ConFin valida tudo o que chega na API (veja util.js). Projetos maiores costumam usar TypeScript, um JavaScript com tipos verificados antes de rodar. É um ótimo próximo passo de estudo.

3Arquitetura: como as peças se organizam

Arquitetura de software é a forma como dividimos o sistema em partes e definimos como elas se comunicam. O ConFin combina alguns padrões clássicos:

3.1 Cliente-servidor

O cliente (o navegador) faz pedidos e o servidor (a API) responde. O cliente nunca acessa o banco diretamente: tudo passa pelo servidor, que é quem aplica as regras e as permissões. Isso é fundamental para a segurança, porque o código que roda no navegador pode ser lido e alterado por qualquer pessoa.

3.2 Arquitetura em três camadas

CamadaResponsabilidadeNo ConFin
ApresentaçãoMostrar dados e capturar ações do usuárioReact (web/src/pages, components)
Aplicação / negócioValidar, aplicar regras, controlar permissõesExpress (api/src/routes, resumo.js, auth.js)
DadosGuardar e recuperar informações com integridadePostgreSQL (schema.sql)

3.3 SPA: aplicação de página única

O ConFin é uma SPA (Single Page Application). O navegador baixa uma vez o HTML, o CSS e o JavaScript do app. Depois disso, ao trocar de tela (Início → Histórico), a página não recarrega: o React só redesenha a parte que mudou e busca os dados (não as telas) na API. Isso deixa a navegação rápida, como num aplicativo nativo.

3.4 API REST

O "contrato" entre front e back é uma API REST: cada recurso tem um endereço (/api/despesas) e usamos os verbos HTTP para dizer o que queremos fazer com ele (detalhes no capítulo 5).

3.5 Monólito modular com um único deploy

Em produção, o próprio servidor Node.js também entrega os arquivos do front-end já compilados (a pasta web/dist). Assim o ConFin inteiro roda num único serviço, com um único endereço. Isso é um monólito: uma aplicação só. Ele é bem organizado em módulos (rotas, autenticação, tempo real, resumo), o que se chama de "monólito modular".

api/src/server.js// Em produção a própria API serve o front-end compilado (web/dist): um único deploy.
if (existsSync(webDist)) {
  app.use(express.static(webDist));                         // arquivos .js, .css, imagens
  app.get(/^\/(?!api|socket\.io).*/, (_req, res) =>          // qualquer outra rota...
    res.sendFile(path.join(webDist, 'index.html')));      // ...devolve o app React
}
Conceito: por que "qualquer outra rota devolve o index.html"? Numa SPA, endereços como /historico não existem como arquivos no servidor: quem decide o que mostrar é o React Router, no navegador. Se o usuário der F5 em /historico, o servidor precisa devolver o index.html para o React assumir. A expressão regular (?!api|socket\.io) garante que as rotas da API não sejam capturadas por essa regra.
Monólito × microsserviços Grandes empresas às vezes dividem o sistema em muitos serviços independentes (microsserviços). Para um time pequeno e um MVP, isso só traria complexidade (vários deploys, comunicação entre serviços, monitoramento). O monólito é a escolha certa aqui, e quase todo sistema começa assim.

4Front-end: React, Vite, Tailwind e PWA

4.1 React: a interface feita de componentes

Conceito React é uma biblioteca (criada pelo Facebook/Meta) para construir interfaces a partir de componentes: funções que recebem dados e devolvem "pedaços de tela". Você descreve como a tela deve ficar para um certo estado, e o React cuida de atualizar o navegador quando o estado muda. Isso se chama programação declarativa.

Os componentes são escritos em JSX, uma sintaxe que mistura JavaScript com algo parecido com HTML:

exemplo simplificadofunction CartaoSaldo({ saldo, percentual }) {
  return (
    <section className="card">
      <p>Saldo disponível</p>
      <p className="text-4xl">{brl(saldo)}</p>      {/* JavaScript dentro de { } */}
      {percentual >= 80 && <span>Atenção: acima de 80%</span>}
    </section>
  );
}

Estado e hooks

Estado é a informação que, quando muda, faz a tela mudar. No React, guardamos estado com hooks, funções especiais que começam com use:

  • useState: guarda um valor (por exemplo, o mês selecionado no Dashboard).
  • useEffect: executa algo depois de desenhar a tela, como buscar dados na API. Ele roda de novo quando alguma das suas dependências muda.
  • useContext: lê um estado global compartilhado por várias telas.
web/src/pages/Dashboard.jsx (simplificado)const { versao } = useApp();                   // muda a cada evento em tempo real
useEffect(() => {
  api(`/despesas/resumo?mes=${mes}`).then(setResumo);  // busca os dados do painel
}, [mes, versao]);                                // ...de novo se o mês ou a versão mudar
No ConFin: o truque da "versão" Quando chega um aviso em tempo real ("o Carlos registrou uma despesa"), o AppContext apenas soma 1 na variável versao. Como o Dashboard tem versao nas dependências do useEffect, ele busca o resumo atualizado sozinho. Assim, qualquer tela que precise reagir a mudanças só precisa "olhar" para a versão.

Context: estado global

Algumas informações são usadas no app inteiro. Em vez de passá-las de componente em componente, usamos Context. O ConFin tem três:

ContextGuarda
AuthContextO usuário logado, login, cadastro e logout
ToastContextOs avisos que aparecem no topo ("Carlos registrou R$ 420,90")
AppContextA conexão de tempo real, a versao, o indicador "Ao vivo" e o formulário de nova despesa

Rotas: qual tela mostrar

O React Router associa endereços a telas. No App.jsx, as rotas mudam conforme a situação do usuário, o que implementa o fluxo de navegação da documentação (seção 7.1):

4.2 Como o front-end conversa com a API

Todas as chamadas passam por uma única função, api(), em web/src/lib/api.js. Centralizar evita repetir código e garante que toda chamada leve o token de login e trate erros do mesmo jeito:

web/src/lib/api.js (resumido)export async function api(rota, { method = 'GET', body } = {}) {

  const res = await fetch('/api' + rota, {
    method,
    headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
    body: body ? JSON.stringify(body) : undefined,

4.3 Vite: a ferramenta de desenvolvimento e build

O navegador não entende JSX diretamente. O Vite faz duas coisas:

  • Em desenvolvimento (npm run dev:web): sobe um servidor em localhost:5173 que converte o código na hora e atualiza a tela assim que você salva um arquivo, sem perder o estado. Isso se chama HMR (Hot Module Replacement).
  • No build (npm run build): gera a pasta web/dist com arquivos otimizados, isto é, minificados (sem espaços e com nomes curtos) e agrupados. É essa pasta que vai para produção.
No ConFin: o proxy do Vite Em desenvolvimento, o front roda na porta 5173 e a API na 3333. Para o front poder chamar /api como se fosse o mesmo endereço, o vite.config.js tem um proxy que repassa /api e /socket.io para a porta 3333. Em produção não é preciso proxy, porque tudo já está no mesmo endereço (seção 3.5).

4.4 Tailwind CSS: estilo com classes utilitárias

Em vez de escrever arquivos CSS separados, o Tailwind oferece classes pequenas que aplicamos direto no JSX: p-4 (espaçamento interno), rounded-2xl (cantos arredondados), text-4xl (texto grande), dark:bg-slate-900 (cor no modo escuro). No build, o Tailwind gera um CSS só com as classes realmente usadas. No web/src/index.css criamos as nossas próprias classes (card, btn-primary, input) com @utility, para padronizar o visual.

Mobile first (RNF002): escrevemos o estilo pensando primeiro no celular e acrescentamos ajustes para telas maiores com prefixos como lg:. Por isso, no celular aparece a barra inferior com o botão "+" e, no computador, o menu lateral.

4.5 Recharts e lucide-react

Recharts desenha os gráficos do Dashboard (a rosca de categorias e as barras dos últimos 6 meses) a partir de arrays de dados. lucide-react fornece os ícones como componentes. As cores das categorias seguem uma paleta testada para daltonismo (web/src/lib/categorias.js), e vermelho e âmbar ficam reservados para os alertas.

4.6 PWA: um site que vira aplicativo

Conceito PWA (Progressive Web App) é um site que o celular pode instalar como um aplicativo: com ícone na tela inicial, abrindo em tela cheia, sem passar pela Play Store ou App Store. Ele precisa de dois ingredientes: um manifest (nome, ícones, cores) e um service worker, um script que roda em segundo plano e guarda em cache os arquivos do app.

O plugin vite-plugin-pwa gera os dois automaticamente a partir do vite.config.js. A regra navigateFallbackDenylist impede que o cache "engula" as chamadas à API e ao Socket.io, que sempre precisam ir ao servidor.

5Back-end: Node.js, Express e a API REST

5.1 Node.js

Node.js é o ambiente que executa JavaScript fora do navegador, usando o mesmo motor do Chrome (V8). Ele traz módulos para rede (node:http), arquivos (node:fs) e caminhos (node:path). Usamos o Node 22 ou superior, que já lê o arquivo .env sozinho (--env-file-if-exists=.env) e reinicia ao salvar (--watch), sem precisar de bibliotecas extras.

5.2 Express: o framework web

Express é um framework minimalista que facilita duas coisas: definir rotas (qual código roda para cada endereço e verbo) e encadear middlewares.

Conceito: middleware Um middleware é uma função que fica "no meio do caminho" da requisição. Ela pode ler e modificar o pedido, barrá-lo com um erro ou passá-lo adiante com next(). As requisições atravessam uma fila de middlewares, como numa linha de montagem.

5.4 Validação: nunca confie no cliente

O formulário do app já impede valores negativos, mas qualquer pessoa pode chamar a API diretamente (com o Postman, por exemplo) e pular o formulário. Por isso a API valida tudo de novo:

api/src/util.js/** Valida valor monetário. RN002: precisa ser positivo. */
export function validarValor(valor) {
  const n = Number(valor);
  if (!Number.isFinite(n)) throw new HttpError(400, 'Valor inválido.');
  if (n <= 0) throw new HttpError(400, 'O valor deve ser maior que zero.');
  return Math.round(n * 100) / 100;            // arredonda para centavos
}

E o banco valida uma terceira vez, com CHECK (valor > 0). São três camadas de defesa: formulário (experiência do usuário), API (segurança) e banco (integridade, a última barreira).

5.5 Tratamento central de erros

Em vez de cada rota tratar seus erros, elas simplesmente lançam um HttpError(status, mensagem). O Express 5 captura erros de funções async e entrega tudo a um único tratador no fim do server.js, que também traduz códigos do PostgreSQL:

api/src/server.jsapp.use((err, _req, res, _next) => {
  if (err.status) return res.status(err.status).json({ erro: err.message });
  if (err.code === '23505') return res.status(409).json({ erro: 'Registro duplicado.' }); // UNIQUE
  if (err.code === '23514') return res.status(400).json({ erro: 'Dados inválidos.' });   // CHECK
  console.error(err);
  res.status(500).json({ erro: 'Erro interno do servidor.' });  // nunca expõe detalhes internos
});

6Autenticação e segurança: bcrypt e JWT

Duas perguntas diferentes que todo sistema precisa responder:

  • Autenticação: quem é você? (login com e-mail e senha)
  • Autorização: o que você pode fazer? (só o admin muda o limite)

6.1 Guardando senhas com bcrypt (RNF003)

Conceito: hash Um hash é uma "impressão digital" de um texto: uma função matemática transforma a senha num código de tamanho fixo, e não existe caminho de volta. Para conferir a senha no login, calculamos o hash do que o usuário digitou e comparamos com o hash guardado. Assim, nem nós (nem quem invadir o banco) sabemos a senha de ninguém.

Por que bcrypt e não SHA-256 (como estava na primeira versão da documentação)?

  • É lento de propósito. O SHA-256 foi feito para ser rápido: uma placa de vídeo testa bilhões de senhas por segundo. O bcrypt tem um fator de custo (usamos 10, ou seja, 210 = 1024 rodadas) que torna cada tentativa cara.
  • Usa salt automaticamente. O salt é um valor aleatório misturado à senha antes do hash. Duas pessoas com a senha "123456" ficam com hashes diferentes, o que inutiliza tabelas prontas de senhas comuns (rainbow tables).
api/src/routes/auth.jsconst senha_hash = await bcrypt.hash(senha, 10);         // cadastro: gera hash + salt
...
await bcrypt.compare(senha, usuario.senha_hash)           // login: confere

// No banco fica algo assim (o salt está embutido no próprio texto):
// $2b$10$N9qo8uLOickgx2ZMRZoMye.IjZAgcfl7p92ldGxad68LJZdL17lhW

6.2 Mantendo o usuário logado com JWT

O HTTP é sem estado (stateless): cada requisição chega ao servidor como se fosse a primeira. Como o servidor sabe que o pedido vem da Ana? Depois do login, o servidor entrega um token JWT (JSON Web Token), e o app o envia em toda requisição seguinte.

Figura 3 — As três partes de um JWT, separadas por pontos.
  • O payload não é secreto (é só Base64, qualquer um lê). Por isso guardamos apenas o id do usuário (sub) e a validade (7 dias), nunca a senha.
  • A assinatura é o que dá segurança: ela é calculada com o JWT_SECRET, que só o servidor conhece. Se alguém alterar o payload (trocar o id para outro usuário), a assinatura não bate e o token é rejeitado.
  • Por isso o JWT_SECRET fica numa variável de ambiente no Render e nunca no código.
api/src/auth.jsexport function gerarToken(usuario) {
  return jwt.sign({ sub: usuario.id }, SECRET, { expiresIn: '7d' });
}
/** Middleware: exige token JWT válido no header Authorization. */
export async function autenticar(req, _res, next) {
  const [tipo, token] = (req.headers.authorization || '').split(' ');  // "Bearer eyJ..."
  if (tipo !== 'Bearer' || !token) throw new HttpError(401, 'Não autenticado.');
  req.usuario = await usuarioDoToken(token);   // confere a assinatura e busca o usuário
  next();
}

7Tempo real: WebSocket e Socket.io

7.1 O problema: o HTTP só responde quando perguntam

No HTTP, a conversa é sempre pedido → resposta, e quem pergunta é o cliente. O servidor não tem como "ligar" para o celular da Ana para avisar que o Carlos gastou algo. Uma solução ingênua seria a Ana perguntar a cada 2 segundos "mudou algo?" (polling). Isso desperdiça bateria, rede e servidor, e ainda tem atraso.

7.2 A solução: WebSocket

Conceito WebSocket é um protocolo que mantém uma conexão aberta nos dois sentidos entre o navegador e o servidor. Depois de conectados, qualquer um dos lados pode enviar mensagens a qualquer momento. É como uma ligação telefônica que fica em aberto, enquanto o HTTP é como mandar cartas.

O Socket.io é uma biblioteca que usa WebSocket e acrescenta recursos práticos: reconexão automática (se o celular perde o sinal, ele reconecta sozinho), eventos com nome e salas.

7.3 Salas: uma por família

Cada família tem uma "sala" (familia:7, por exemplo). Quando alguém se conecta, o servidor confere o token e coloca a pessoa na sala da família dela. Para avisar uma família, o servidor fala só com aquela sala, e as outras famílias nunca recebem nada.

api/src/realtime.jsio.use(async (socket, next) => {                   // "porteiro": só entra com token válido

io.on('connection', (socket) => {

Decisão de projeto: o evento é só um "sinal" O evento traz a despesa e o saldo, mas o Dashboard busca o resumo completo de novo pela API REST. Por quê? Assim existe uma única fonte da verdade (o banco, via API). Se um evento se perder (o celular estava sem sinal), na próxima atualização a tela fica certa do mesmo jeito. Se um dia o ConFin rodar em várias instâncias ao mesmo tempo, será preciso um "adaptador" (por exemplo, com Redis) para que um servidor avise os usuários conectados aos outros. Com uma instância só, como hoje, isso não é necessário.

8Banco de dados: PostgreSQL e o nosso modelo

8.1 Por que um banco relacional?

Conceito Um banco de dados relacional organiza os dados em tabelas (linhas e colunas) que se relacionam por chaves. Ele é consultado com SQL e garante as propriedades ACID: Atomicidade (tudo ou nada), Consistência (as regras sempre valem), Isolamento (operações simultâneas não se atrapalham) e Durabilidade (o que foi confirmado não se perde).

Dados financeiros são estruturados e cheios de relações (despesa → usuário → família), e somas precisam ser exatas. O PostgreSQL é um banco relacional gratuito, de código aberto, muito robusto e oferecido de graça por serviços como o Supabase. Um banco NoSQL (como o MongoDB) seria mais flexível, mas abriria mão de garantias que aqui são valiosas.

8.2 O modelo: a família no centro

Figura 4 — Modelo entidade-relacionamento do ConFin (🔑 chave primária, 🔗 chave estrangeira).

Lendo o diagrama: uma família tem muitos usuários, uma família tem muitas despesas, um usuário registra muitas despesas e uma família tem muitos convites pendentes. Essa foi justamente a solução do problema registrado no diário de bordo (12.3): como dois usuários veriam o mesmo saldo? Colocando a família como entidade central. 8.3 As tabelas em detalhe

api/db/schema.sql (trechos)CREATE TABLE IF NOT EXISTS despesa (
  id              SERIAL PRIMARY KEY,                        -- número automático, único
  valor           NUMERIC(12,2) NOT NULL CHECK (valor > 0),  -- RN002
  data            DATE NOT NULL DEFAULT CURRENT_DATE,
  categoria       VARCHAR(20) NOT NULL CHECK (categoria IN ('MERCADO', 'MORADIA', ...)),
  meio_pagamento  VARCHAR(10) NOT NULL CHECK (meio_pagamento IN ('CREDITO','DEBITO','PIX','DINHEIRO')),
  descricao       VARCHAR(120),                               -- opcional (aceita NULL)
  usuario_id      INT REFERENCES usuario(id) ON DELETE SET NULL,
  familia_id      INT NOT NULL REFERENCES familia(id) ON DELETE CASCADE,
  criado_em       TIMESTAMPTZ NOT NULL DEFAULT now()
);

Decisões importantes, uma a uma

  • NUMERIC(12,2) para dinheiro, nunca FLOAT. Números de ponto flutuante são aproximados em binário: em JavaScript, 0.1 + 0.2 dá 0.30000000000000004. NUMERIC guarda valores decimais exatos, com até 12 dígitos, 2 deles depois da vírgula. Somar milhares de despesas não "perde centavos".
  • Chave primária (PRIMARY KEY): identifica cada linha de forma única. SERIAL gera 1, 2, 3... automaticamente.
  • Chave estrangeira (REFERENCES): garante que familia_id aponte para uma família que existe. Isso é a integridade referencial.
  • ON DELETE CASCADE (despesa → família): se a família for apagada, as despesas dela vão junto, porque não fazem sentido sozinhas.
  • ON DELETE SET NULL (despesa → usuário): se um membro sair do sistema, as despesas dele continuam na família (o dinheiro foi gasto!), só perdem o autor. No Dashboard, aparecem como "Ex-membro".
  • CHECK e UNIQUE como regras de negócio: email UNIQUE é a RN001, CHECK (valor > 0) é a RN002. Mesmo que a API tenha um bug, o banco recusa dados inválidos.
  • TIMESTAMPTZ: data e hora com fuso horário, para registrar quando cada linha foi criada.
  • Normalização: cada informação fica num lugar só. O nome do usuário está em usuario, e a despesa guarda apenas o usuario_id. Se a pessoa mudar o nome, não é preciso atualizar milhares de despesas.

Índices: o "sumário" das tabelas

CREATE INDEX IF NOT EXISTS idx_despesa_familia_data ON despesa (familia_id, data);

Sem índice, para achar as despesas de novembro da família 7, o banco leria a tabela inteira. O índice funciona como o índice remissivo de um livro: vai direto às linhas certas. Escolhemos (familia_id, data) porque quase toda consulta do app filtra exatamente por família e período.

8.4 Como o servidor conversa com o banco

Pool de conexões

Abrir uma conexão com o banco é lento (rede, autenticação, SSL). O pg.Pool mantém algumas conexões abertas e reutilizáveis: cada consulta "pega emprestada" uma conexão e devolve ao terminar.

api/src/db.jsexport const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,                     // onde está o banco
  ssl: process.env.DATABASE_SSL === 'true' ? { rejectUnauthorized: false } : undefined,
});

Consultas parametrizadas: a defesa contra SQL Injection

Nunca faça isto query("SELECT * FROM usuario WHERE email = '" + email + "'")
Se alguém digitar no e-mail ' OR '1'='1, a consulta vira ... WHERE email = '' OR '1'='1', que é sempre verdadeiro. Isso é SQL Injection, um dos ataques mais comuns da web.
o jeito certo, usado em todo o ConFinquery('SELECT * FROM usuario WHERE email = $1', [email]);
-- O texto do SQL e os valores viajam SEPARADOS. O banco trata $1 sempre como dado,
-- nunca como comando, não importa o que o usuário digite.

Transações: tudo ou nada

No cadastro, se o e-mail tinha um convite pendente, fazemos três operações: verificar o convite, criar o usuário já na família e apagar o convite. Se a terceira falhar, não podemos ficar com um estado "pela metade". A transação (BEGIN … COMMIT, ou ROLLBACK em caso de erro) garante que ou tudo acontece, ou nada acontece: é o "A" do ACID.

api/src/db.jsexport async function transacao(fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const resultado = await fn(client);
    await client.query('COMMIT');           // confirma tudo
    return resultado;
  } catch (err) {
    await client.query('ROLLBACK');         // desfaz tudo
    throw err;
  } finally { client.release(); }          // devolve a conexão ao pool
}

8.5 A consulta mais importante: o saldo do mês

Esta é a lógica central descrita na seção 10 da documentação. Vale ler devagar:

api/src/resumo.js — saldoDoMes()SELECT f.limite_mensal AS limite,
       COALESCE(SUM(d.valor), 0) AS total            -- soma; se não houver despesa, 0
  FROM familia f
  LEFT JOIN despesa d ON d.familia_id = f.id          -- junta as despesas da família...
       AND d.data >= $2::date                         -- ...a partir do dia 1 do mês
       AND d.data <  $2::date + INTERVAL '1 month'     -- ...até antes do dia 1 do mês seguinte
 WHERE f.id = $1
 GROUP BY f.id
  • LEFT JOIN (e não JOIN): mantém a família no resultado mesmo que ela não tenha nenhuma despesa no mês. Com um JOIN comum, uma família sem despesas sumiria do resultado.
  • COALESCE(SUM(...), 0): a soma de "nada" em SQL é NULL, não 0. O COALESCE troca NULL por 0.
  • Intervalo >= início e < início + 1 mês: funciona para meses de 28, 30 ou 31 dias, sem precisar calcular o último dia, e aproveita o índice (familia_id, data).

Depois, em JavaScript: saldo = limite − total, percentual = total ÷ limite × 100 e o nível de alerta (RN004):

export function nivelAlerta(percentual) {
  if (percentual >= 100) return 'ESTOURADO';
  if (percentual >= 80)  return 'ATENCAO';
  return 'OK';
}

O Dashboard roda seis consultas em paralelo com Promise.all (saldo, por categoria, por membro, por meio de pagamento, últimos 6 meses e últimas transações), em vez de uma depois da outra. O gráfico de 6 meses usa generate_series, uma função do PostgreSQL que gera a lista de meses, para que meses sem gasto também apareçam (com zero).

8.6 Detalhes que evitam bugs sutis

  • Datas sem fuso: o tipo DATE é devolvido como texto '2026-11-09' (db.js). Se virasse um objeto Date do JavaScript, o fuso horário poderia transformar "9 de novembro" em "8 de novembro, 21h".
  • "Hoje" no fuso de Brasília: o servidor do Render está nos EUA, com outro horário. O util.js calcula "hoje" e "mês atual" em America/Sao_Paulo; senão, uma despesa lançada às 22h do dia 30 poderia cair no mês seguinte.
  • Schema idempotente: o schema.sql usa CREATE TABLE IF NOT EXISTS e roda toda vez que o servidor liga (aplicarSchema()). Rodar uma ou dez vezes dá o mesmo resultado: é isso que "idempotente" quer dizer.
  • RLS (Row Level Security): o Supabase cria automaticamente uma API pública para as tabelas. Ligamos o RLS sem nenhuma política, o que bloqueia esse acesso. Só a nossa API, que conecta como dona das tabelas, consegue ler e gravar.

9.3 O que o Supabase faz

O Supabase hospeda um PostgreSQL de verdade na nuvem (região us-east-1, nos EUA), com backup e SSL. Ele também oferece login, armazenamento de arquivos e uma API automática, mas usamos só o banco, porque a nossa API faz o resto. No plano gratuito, o projeto pausa após 7 dias sem uso e precisa ser restaurado no painel.

9.4 Como o Render se liga ao Supabase

A ligação é feita por uma única informação: a connection string, guardada na variável DATABASE_URL. Ela é como um "endereço completo com chave" do banco:

Figura 5 — Anatomia da DATABASE_URL (com a senha substituída por SENHA).
  • Por que "Session pooler"? A conexão direta do Supabase só funciona por IPv6, e o Render só tem IPv4. O pooler é um intermediário que aceita IPv4 e repassa a conexão. O modo Session (porta 5432) mantém uma conexão por cliente, o que combina com o nosso servidor, que fica ligado o tempo todo e tem seu próprio pool.
  • SSL: com DATABASE_SSL=true, todo o tráfego entre o Render (na Virgínia) e o Supabase (na mesma região) é criptografado. Colocar os dois na mesma região reduz a latência de cada consulta.
  • As tabelas se criam sozinhas: na primeira vez que o servidor liga no Render, o aplicarSchema() executa o schema.sql no Supabase.

10Uma despesa de ponta a ponta

Agora juntamos tudo. Este é o caminho completo do momento em que o Carlos toca em Salvar até o celular da Ana mostrar o alerta, que é exatamente a cena da demonstração do pitch:

  1. Formulário (web/src/components/DespesaSheet.jsx): o Carlos digita R$ 420,90 com a máscara de moeda. O componente já mostra a prévia ("depois desta despesa sobram R$ 839,11") e impede o envio de valor zero.
  2. Chamada HTTP (web/src/lib/api.js): POST /api/despesas com o JSON da despesa e o cabeçalho Authorization: Bearer <token do Carlos>. Viaja por HTTPS até o Render.
  3. Middlewares (server.js, auth.js): o JSON é lido; o autenticar confere a assinatura do token e descobre que é o Carlos; o exigirFamilia confirma que ele tem família.
  4. Validação (validarDespesa em routes/despesas.js): valor > 0 (RN002), categoria e meio de pagamento válidos, data no formato certo.
  5. Gravação: INSERT INTO despesa ... VALUES ($1, $2, ...), uma consulta parametrizada, pelo pool de conexões, com SSL, até o Supabase. O banco confere o CHECK e as chaves estrangeiras.
  6. Novo saldo (resumo.js): a consulta do saldo do mês calcula total = R$ 3.660,89, ou seja, 81,4% do limite → alerta ATENCAO (RN004).
  7. Aviso em tempo real (realtime.js): notificarFamilia() emite familia:mudou para a sala familia:<id>, com a despesa e o saldo.
  8. Resposta ao Carlos: 201 Created com a despesa e o saldo. O formulário fecha e a tela dele atualiza. É o cenário alternativo do UC002: passar do limite é permitido, mas gera alerta.
  9. O celular da Ana recebe o evento (AppContext.jsx), que estava conectado por WebSocket o tempo todo: aparece o aviso "Carlos registrou R$ 420,90", e a versao sobe.
  10. O Dashboard da Ana se atualiza (Dashboard.jsx): como versao mudou, o useEffect chama GET /api/despesas/resumo e a tela é redesenhada com R$ 839,11, a barra amarela e o selo "Atenção: acima de 80%". Ninguém recarregou a página.

Tudo isso acontece, em geral, em menos de um segundo, o que atende ao RNF001 (resposta em até 2 segundos).

11Ferramentas do dia a dia: Git, npm e scripts

11.1 Git e GitHub

  • Git é um controle de versão: guarda o histórico de todas as mudanças (commits), permite voltar no tempo e trabalhar em equipe sem um sobrescrever o outro.
  • GitHub é o site que hospeda o repositório na nuvem. É de lá que o Render baixa o código.
  • Comandos essenciais: git status (o que mudou), git add + git commit -m "..." (salvar uma versão), git push (enviar ao GitHub, o que dispara o deploy), git pull (baixar o que os outros enviaram).
  • O .gitignore lista o que não vai para o GitHub: node_modules/ (pesado, reinstalável), dist/ (gerado no build) e .env (segredos).

11.2 npm e o package.json

  • npm é o gerenciador de pacotes do Node: baixa as bibliotecas (dependências) para a pasta node_modules.
  • package.json lista as dependências e os scripts. dependencies são necessárias para rodar; devDependencies, só para desenvolver (por exemplo, o Vite e o PostgreSQL embutido).
  • package-lock.json "congela" as versões exatas instaladas, para que o Render instale exatamente o mesmo que o seu PC (npm ci usa esse arquivo).
  • Versões como ^5.3.0 seguem o versionamento semântico (MAIOR.MENOR.CORREÇÃO): o ^ aceita atualizações que não quebram compatibilidade.

13Perguntas que a banca pode fazer

Por que JavaScript e não Java, C# ou Python?Porque é a única linguagem que roda no navegador. Usando Node.js no servidor, a equipe trabalha com uma única linguagem nas duas pontas, e o ecossistema (React, Express, Socket.io) é maduro e gratuito.
Como funciona o tempo real?Com WebSocket, via Socket.io. Cada celular mantém uma conexão aberta com o servidor e entra numa "sala" da sua família. Quando alguém registra uma despesa, o servidor avisa a sala, e as telas buscam o resumo atualizado pela API.
Como garantem que uma família não vê os dados da outra?O id da família vem do token JWT do usuário logado, nunca de um parâmetro enviado pelo navegador, e todas as consultas filtram por ele. No tempo real, cada família tem a sua sala, e só entra quem tem um token válido.
Como as senhas são armazenadas?Como hash bcrypt com custo 10 e salt automático. Não é possível recuperar a senha a partir do hash. Trocamos o SHA-256 da primeira versão porque ele é rápido demais e facilita ataques de força bruta.
Por que PostgreSQL? Por que não NoSQL?Os dados são estruturados e relacionados (família → usuários → despesas), e as somas de dinheiro precisam ser exatas. O banco relacional garante integridade (chaves estrangeiras, UNIQUE, CHECK) e transações ACID. Usamos NUMERIC(12,2) para não ter erro de arredondamento.
Onde estão as regras de negócio?Em camadas: no formulário (experiência do usuário), na API (validação e permissões) e no banco (CHECK e UNIQUE, a última barreira). Por exemplo, a RN002 está nas três.
Por que Render e não AWS, como estava na documentação?O Render é um PaaS: entregamos o código e ele cuida do servidor, do HTTPS e do deploy automático a cada push, com custo zero. Na EC2 (IaaS) teríamos que configurar sistema operacional, servidor web, certificado e processo manualmente. A AWS fica como evolução futura.
O que acontece se o usuário passar do limite?O sistema permite registrar (o gasto aconteceu de verdade), mas mostra o alerta. É o cenário alternativo do UC002. Os alertas aparecem em 80% (atenção) e 100% (estourado), conforme a RN004.
E se a internet do celular cair?O selo "Ao vivo" muda para "Offline" e o Socket.io reconecta sozinho quando o sinal volta. Como as telas sempre buscam os dados da API, ao reconectar elas mostram o estado correto.
Como vocês testaram?Com um teste automatizado de ponta a ponta (smoke test) que cobre cadastro, login, e-mail duplicado, valor negativo, permissões e cálculo do saldo, além de testes manuais com dois usuários simultâneos para validar o tempo real.

14Exercícios práticos e trilha de estudo

A melhor forma de aprender é mexer no próprio projeto. Faça cada exercício numa branch separada (git checkout -b estudo-1), para não afetar a main nem o deploy. Estão em ordem de dificuldade:

  1. Mude um texto e veja o HMR. Com npm run dev:web rodando, altere "Resumo da família" no Dashboard.jsx e salve. A tela muda sem recarregar.
  2. Explore a API "na mão". Abra http://localhost:3333/api/health no navegador. Depois, use a extensão Thunder Client do VS Code para fazer login (POST /api/auth/login) e chamar /api/despesas/resumo com o token.
  3. Teste a defesa da API. Envie uma despesa com "valor": -10 direto para a API e veja o erro 400. Depois, tente com um token de um membro alterar o limite (PATCH /api/familias/minha) e veja o 403.
  4. Consulte o banco com SQL. Instale o DBeaver (gratuito), conecte em localhost:5433 (usuário e senha postgres, banco confin) e escreva consultas: total gasto por categoria, quem gastou mais no mês, a maior despesa.
  5. Escreva um teste unitário para nivelAlerta() com o executor de testes do próprio Node (node --test): 79,9 → OK; 80 → ATENCAO; 100 → ESTOURADO.
  6. Adicione uma categoria ("Pets"). Você vai precisar mexer no CHECK do schema.sql, no util.js e no categorias.js do front, o que mostra como uma mudança atravessa as três camadas. Repare também no problema das migrations (capítulo 12).
  7. Crie um endpoint novo: GET /api/despesas/exportar?mes=AAAA-MM, que devolve um CSV para abrir no Excel. Pratica rotas, consulta SQL e cabeçalhos HTTP (Content-Type: text/csv).
  8. Desafio: limite de gasto por categoria, com alerta próprio. Envolve modelagem (uma tabela nova), API, tempo real e interface: o ciclo completo.

15Glossário

API
Interface de Programação de Aplicações: o "contrato" de como um programa conversa com outro.
Back-end
A parte do sistema que roda no servidor: regras, dados, segurança.
Build
Processo que transforma o código-fonte em arquivos otimizados prontos para produção.
CI/CD
Integração e entrega/deploy contínuos: testar e publicar automaticamente a cada mudança.
Componente
Peça reutilizável de interface no React (uma função que devolve JSX).
Connection string
Texto com tudo o que é preciso para conectar a um banco (usuário, senha, servidor, porta).
CORS
Regra do navegador que controla quais sites podem chamar uma API.
Deploy
Publicar uma versão do sistema no ambiente de produção.
Endpoint
Um endereço da API com um verbo, por exemplo POST /api/despesas.
Front-end
A parte do sistema que o usuário vê, que roda no navegador.
Hash
Transformação de mão única de um texto num código fixo (usado nas senhas).
Health check
Endereço que diz se o serviço está funcionando (/api/health).
Hook
Função do React que começa com use e dá "poderes" aos componentes (estado, efeitos).
Idempotente
Operação que dá o mesmo resultado se executada uma ou várias vezes.
Índice
Estrutura que acelera buscas no banco, como o índice de um livro.
JSON
Formato de texto para trocar dados entre front e back.
JWT
Token assinado que prova quem é o usuário em cada requisição.
Middleware
Função no meio do caminho da requisição, que pode barrar ou passar adiante.
Monólito
Sistema publicado como uma única aplicação.
ORM
Biblioteca que gera SQL a partir de objetos (não usamos: escrevemos o SQL à mão).
PaaS / IaaS
Plataforma pronta para código / máquina virtual "crua" (ver capítulo 9).
Pool de conexões
Conjunto de conexões com o banco reaproveitadas entre consultas.
PWA
Site instalável como aplicativo, com manifest e service worker.
REST
Estilo de API baseado em recursos, verbos HTTP e códigos de status.
RLS
Row Level Security: regras do PostgreSQL sobre quem acessa cada linha.
Salt
Valor aleatório misturado à senha antes do hash.
Seed
Script que popula o banco com dados de exemplo.
SPA
Aplicação de página única: troca de tela sem recarregar.
SQL Injection
Ataque que insere comandos SQL por um campo de texto. Evitado com parâmetros.
Transação
Grupo de operações no banco que acontece por completo ou não acontece.
WebSocket
Conexão aberta e bidirecional entre navegador e servidor.
